## 1. 검토 범위

Design V&V 3개 Task(추적성 분석, 소프트웨어 설계 평가, 인터페이스 분석)를 SAD 전체와 ADR 4건에 적용했다. SAD-only 정책(§4.7)에 따라 SDD 상세는 검증하지 않았고, `docs/3.Design/SDD.md`에는 `명시 결정` 블록이 없음을 확인했다(`grep` 0건). 코드는 SAD `현행 코드 대응` 표의 사실 여부 확인에만 사용했으며 구현 V&V는 수행하지 않았다.

적용 렌즈(Review mode): Completeness/Traceability, Correctness/Accuracy, Consistency/Interfaces, Readability/Unambiguity, Testability/Evidence.

제외: 구현 V&V, 시험 설계·실행, PRD/SRS 자체의 요구사항 V&V(상위 결함은 설계 판정에 영향을 주는 범위에서만 기록), 위험·보안 분석.

## 4. 발견사항

### D-01 `<SRS-F043>` 원자 저장 책임 배정 불일치

문제: `SAD-C011`은 "file format and atomic replace"를 `SAD-C002` 책임으로 넘기나, `SAD-C002` 책임·`구현요건`에는 `<SRS-F043>`과 임시 파일 교체가 없다. 추적표도 `<SRS-F043>` → `SAD-C011`, `SAD-I002`만 연결.
근거: `SAD.md:191`, `SAD.md:193`, `SAD.md:466`, `SAD.md:577`, `SAD.md:287`
영향: 원자 저장 소유 컴포넌트가 문서상 둘로 갈려 구현·시험 배정 혼선.
필요한 수정 또는 확인: `SAD-C002` `구현요건`·책임에 `<SRS-F043>` 반영 또는 소유 컴포넌트 단일화. 소유 단계: docs(SAD).

### D-04 관리대장 행 기록 실패 시 상태·파일 위치 미결

문제: `SAD-C005` 순서는 분류 → 배치 → 대장 → 로그이고 `SAD-I005`는 "per-row write failure marks that file `Error`"라 한다. 이 경우 파일은 이미 이동된 뒤라 `<SRS-F025>`("`Error` 파일은 이동하지 않고 `source_root` 보존")와 충돌하고, 기록 실패 행은 `<SRS-N005>`(행 수 = 대상 수)를 만족할 수 없다. `<SAD-Q007>`이 워크북을 1회 열기로 하면 저장 시점 실패가 이미 이동된 전체 파일에 영향.
근거: `SAD.md:219-220`, `SAD.md:315`, `SAD.md:391`, `SRS.md:364-367`, `SRS.md:357-360`, `SRS.md:517-518`

필요한 수정 또는 확인: SRS가 `<SRS-F025>`의 "관리대장 행 기록 실패"와 "이동하지 않음"의 순서 관계를 확정한 뒤 SAD가 기록·저장 시점을 결정. 소유 단계: docs(SRS 우선, 이어서 SAD).

영향: UI 통과·실행 차단 차이의 실제 범위가 SRS 해석에 좌우.
필요한 수정 또는 확인: SRS가 (4)의 대상(디렉토리 자체 vs 상위)을 확정. SAD는 헤더 검사 차이 추가. 소유 단계: docs(SRS 우선).

### 9.3 발견사항

#### D-12 부록 A와 `상위요건` 불일치

문제: 부록 A가 `<PRD-F019>`에 `<SRS-F031>`·`<SRS-F035>`·`<SRS-F040>`을, `<PRD-N005>`에 `<SRS-F025>`를 연결한다. 그러나 해당 SRS 항목의 `상위요건:` 줄에는 이 PRD ID가 없다. `77d4d24` 기준에서는 이 둘이 완전히 일치했다.
근거: `SRS.md:879`, `SRS.md:886`, `SRS.md:412`, `SRS.md:448`, `SRS.md:485`, `SRS.md:508`
영향: 양방향 추적 불일치. 게이트는 PRD 커버만 검사하므로 통과한다.
필요한 수정 또는 확인: 해당 `상위요건:` 줄에 PRD ID를 추가하거나 부록 A에서 제거. 소유 단계: docs(SRS).
결과: FAIL (경미)

#### D-13 "세션당 1회 처리"가 코드 동작으로 잘못 기술됨

문제: `<SRS-F009>`와 `SAD-C004`는 같은 (경로, 크기, 수정 시각)을 "한 감시 세션에서 1회" 처리한다고 쓰고, 부록 B는 이를 "현행 코드 동작을 그대로 기술"했다고 한다. 실제 코드에서는 감시기 객체가 프로그램당 1개이고 시그니처 집합이 `start()`에서 비워지지 않는다. 따라서 중복 억제가 프로세스 수명 전체에 걸린다. 이 차이는 `현행 코드 대응` 표에도 없다.
근거: `SRS.md:259`, `SRS.md:908`, `SAD.md:224`, `file_watcher.py:30`, `file_watcher.py:35-42`, `file_watcher.py:116-119`, `main.py:111`
영향: 감시를 중지했다 다시 시작해도, `Error`로 `source_root`에 남은 미변경 파일은 재처리되지 않는다(코드). 문서상으로는 재처리된다.
필요한 수정 또는 확인: 부록 B 문구를 "설계 적응"으로 바꾸고 `현행 코드 대응` `SAD-C004` 행에 추가할 것. 또는 SRS를 코드 동작(프로세스당 1회)으로 바꿀 것. 소유 단계: docs(SRS, SAD).
결과: FAIL (경미, 표시 누락)

#### D-14 `app.config.yaml` 부재·파싱 실패 동작이 SRS에 없음

문제: SRS §8.2.1은 두 키를 선택 사항으로 두지만, 파일 자체가 없거나 파싱에 실패할 때의 동작을 정하지 않는다. `<SRS-F004>` (6)은 값 범위만 검사한다. `SAD-I002`는 "missing file or parse error blocks startup (exit 1)"을 두 파일 모두에 적용해, SRS에 없는 동작을 확정한다. 코드는 파일이 없으면 예외로 종료한다.
근거: `SRS.md:693-701`, `SAD.md:310`, `config_loader.py:35-39`, `main.py:121`
영향: 기본값 사용과 기동 차단 중 어느 쪽이 요구인지 불명확하다.
필요한 수정 또는 확인: SRS에서 부재·파싱 실패 처리를 확정(코드는 차단). 소유 단계: docs(SRS).
결과: REVIEW_REQUIRED

#### D-15 관리대장 헤더 검사 시점의 SRS·SAD 불일치

문제: SRS §8.4는 헤더 누락 시 "`<SRS-F004>`가 실행을 차단"한다고 한다. `<SRS-F004>`는 프로그램 기동 시 검사이고, 실패하면 GUI도 열지 않는다. 반면 SAD는 헤더 검사를 세션 시작 단계 6에 두고, GUI에서는 "session not started"로 처리한다. 또 `SAD-I005`는 헤더 누락을 일괄 "exit 1"로 써서 SAD 내부에서도 GUI 동작이 다르게 읽힌다.
근거: `SRS.md:745-746`, `SAD.md:154`, `SAD.md:337`
영향: GUI 모드에서 헤더 누락 시 창 미기동인지 세션 미시작인지 불명확하다.
필요한 수정 또는 확인: SRS §8.4의 검사 시점을 감시 세션 시작으로 정정하고(`<SRS-F033>`과 일치), `SAD-I005`를 모드별로 정리. 소유 단계: docs(SRS 우선, SAD).
결과: REVIEW_REQUIRED
